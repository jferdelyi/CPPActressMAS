# ThreadSanitizer suppressions for the ordinary tests (unit, integration, mqtt) of CPPActressMAS.
# Format: https://github.com/google/sanitizers/wiki/ThreadSanitizerSuppressions
#
# Each entry documents a KNOWN race with its ID (docs/port/00-analyse-initiale.md) and is removed in the
# mission that fixes it. The characterization crash probes never use this file: they must see these races.
# Entries are added only once the race has been observed under the tsan preset.
#
# 1C removed the entries of T3 and T4 (Paho callbacks touching the agent collection and the container
# set): the transport layer applies everything at the turn boundary.

# T8 (dependency, 2A): Paho C 1.3.13 reads and writes its global sendThread_state from its send and
# receive threads without synchronisation (MQTTAsyncUtils.c:1817 against :2325), seen once three clients
# of one process connect. Paho C is instrumented with the project (CMAKE_C_FLAGS of the tsan preset); the
# race is inside Paho, not in CPPActressMAS. Reported in docs/port/BACKLOG.md; to drop with a Paho fix.
race:MQTTAsync_sendThread
race:MQTTAsync_receiveThread

# T10 (dependency, 2A, Linux): zenoh-c embeds the Rust runtime (zenoh, tokio), which is not instrumented
# and synchronises through futex calls that ThreadSanitizer does not see, so every memcpy, write, recv or
# free issued from that code looks unsynchronised (237 reports on zenoh.network under gcc, both accesses
# inside the Rust code every time, none in CPPActressMAS). The shared library is linked on Linux so that
# this entry ignores the interceptors called from it and nothing else: a race between two CPPActressMAS
# frames stays visible (T9 was found that way). Ignoring the library also hides the thread creations it
# makes, so the hand-over of a closure to a Zenoh thread is marked in ZenohTransport.cpp with
# __tsan_release / __tsan_acquire (release_to_callbacks, acquire_from_declarer). Inert on macOS, where
# zenoh-c is linked statically and produced no report. Reported in docs/port/BACKLOG.md.
called_from_lib:libzenohc.so
# Still T10: zenoh-cpp allocates the closure object (into_context) inside the declare call, so the first
# callback may run before the declaring thread reaches its release. Only the reports whose stack holds that
# allocation are suppressed: a race on any other data stays visible.
race:into_context
